# 常规设置页设计

> 日期: 2026-04-18  
> 状态: 已批准（对话确认）  
> 范围: 第一版

## 概述

在现有设置体系中新增一个独立的顶级页 `常规设置`，作为设置默认入口，用于承载全局应用级偏好，而不是工作区级或 agent/system 级配置。第一版聚焦三类高频项：

1. 界面：主题模式
2. 窗口行为：最小化到系统托盘、关闭到系统托盘
3. 维护：打开日志目录、清理缓存

这一页的目标不是做“大而全”的控制台，而是建立一个稳定的、可扩展的常规偏好入口，并为后续继续增加语言、下载目录、通知等通用项预留结构。

## 背景与问题

当前设置页导航仅包含：

- 供应商配置
- Agent
- MCP
- 关于

这些页面大多偏向模型、能力和系统接入层，但缺少一个面向普通桌面使用习惯的入口。像主题、系统托盘行为、日志目录、缓存维护这类能力虽然天然属于“应用常规设置”，却没有合适的归位。

如果继续把这些能力散落在 Agent / 关于 / 系统配置中，会带来几个问题：

- 语义混乱：桌面应用偏好和 agent 运行配置混在一起
- 扩展困难：后续想加语言、下载目录、通知时没有稳定落点
- 用户心智负担高：不知道“这到底算设置里的哪一类”

因此需要新增一个顶级常规设置页，专门承载全局应用偏好和维护动作。

## 信息架构

### 导航层级

新增一个独立顶级 tab：`常规设置`

导航顺序：

1. 常规设置
2. 供应商配置
3. Agent
4. MCP
5. 关于

选择这个位置的原因：

- `常规设置` 是更接近“应用入口”的页面，适合作为设置默认首页
- 它与 `供应商配置 / Agent / MCP` 的语义不同，不应该作为子块塞进 Agent 页
- 后续扩展也最自然

### 页面结构

右侧内容区保持现有设置页的视觉语言，不引入新容器体系：

- 页面标题：`常规设置`
- 副标题：`管理界面偏好、窗口行为和本地维护操作`
- 使用纵向卡片布局，自上而下排列三个区块：
  - 界面
  - 窗口行为
  - 维护

## 详细设计

### 一、界面区块

#### 条目

- 主题模式

#### 表现形式

三选一卡片：

- 跟随系统
- 浅色
- 深色

#### 行为

- 点击即生效
- 点击后立即持久化
- 成功后轻量提示：`主题已更新`
- 失败则回滚到上一个值并提示失败

#### 数据模型

```ts
themeMode: "system" | "light" | "dark"
```

#### 作用域

全局应用级，不按工作区区分。

### 二、窗口行为区块

#### 条目

- 最小化到系统托盘
- 关闭到系统托盘

#### 表现形式

两个独立的设置行：

- 左侧：标题 + 简短说明
- 右侧：Switch 开关

#### 说明文案方向

- 最小化到系统托盘：开启后最小化时不只停留在任务栏，而是进入系统托盘
- 关闭到系统托盘：开启后点击关闭按钮不会直接退出，而是隐藏到系统托盘

#### 行为

- 开关变化后立即保存
- 允许乐观更新
- 如果后端保存失败，则回滚并 toast 提示

#### 数据模型

```ts
windowBehavior: {
  minimizeToTray: boolean
  closeToTray: boolean
}
```

#### 作用域

全局应用级，不按工作区区分。

### 三、维护区块

#### 条目 1：打开日志目录

表现形式：

- 一个动作行
- 右侧按钮文案：`打开`

行为：

- 点击后直接使用系统文件管理器打开日志目录
- 成功不强制 toast
- 失败时显示错误提示

#### 条目 2：清理缓存

表现形式：

- 一个动作行
- 右侧按钮文案：`清理`

点击后：

- 打开 modal 弹层
- 弹层内提供三项勾选项，默认全选：
  - 前端临时缓存
  - 预览/渲染缓存
  - 日志缓存

#### 弹层行为

- 标题：`清理缓存`
- 副说明：明确写出“不影响会话、线程、工作区和配置”
- 主按钮：`执行清理`
- 取消按钮：`取消`
- 如果一个选项都没勾选，主按钮禁用
- 执行后反馈清理结果，建议按项目列出已清理项

#### 缓存清理边界

第一版只允许清理以下“安全缓存”：

- 前端临时缓存
- 预览/渲染缓存
- 日志缓存

第一版明确不碰：

- 会话/对话数据
- agent 线程数据
- 工作区文件
- `lume.yaml`
- 渠道配置
- MCP 配置

## 状态与持久化

### 总体原则

第一版不新建独立配置文件，而是直接扩展现有 `settings.json`。

但为了避免和 `uiState` 混淆，新增独立命名空间：

```ts
generalSettings: {
  themeMode?: "system" | "light" | "dark"
  windowBehavior?: {
    minimizeToTray?: boolean
    closeToTray?: boolean
  }
}
```

### 为什么不用 `uiState`

`uiState` 当前更适合保存瞬时界面状态，比如：

- 当前视图
- 当前对话 ID
- 草稿内容
- 面板开合状态

而常规设置属于稳定偏好：

- 主题模式
- 窗口行为

如果直接混进 `uiState`，语义会越来越模糊，后续维护成本会上升。

### 为什么不用 `lume.yaml`

这页中的项本质是桌面应用偏好，不是：

- agent 运行策略
- provider/model 选择
- workspace 级配置

因此不应混入 `lume.yaml` 这类业务/系统配置。

## 系统职责分层

### Web

负责：

- 渲染常规设置页面
- 即时更新 UI
- 管理局部 loading/disabled 状态
- 触发 toast 反馈

不负责：

- 托盘行为逻辑
- 文件系统清理细节
- 窗口事件拦截

### Sidecar

负责：

- 读写 `generalSettings`
- 暴露获取/更新常规设置的 RPC
- 暴露：
  - 打开日志目录
  - 清理缓存

### Desktop / Tauri

负责：

- 真正执行窗口行为
- 拦截窗口最小化 / 关闭事件
- 根据 `generalSettings.windowBehavior` 决定：
  - 进入系统托盘
  - 还是直接退出/最小化

## 交互原则

### 偏好类

适用于：

- 主题模式
- 窗口行为

规则：

- 设置即时生效
- 同时即时持久化
- 不额外设置全页“保存”按钮

### 动作类

适用于：

- 打开日志目录
- 清理缓存

规则：

- 用户显式点击才执行
- `清理缓存` 必须二次确认
- 执行后给出结果反馈

## 错误处理

### 主题模式保存失败

- 回滚到旧值
- toast：`主题更新失败`

### 窗口行为保存失败

- 对应开关回滚
- toast：`窗口行为更新失败`

### 打开日志目录失败

- toast：`打开日志目录失败`

### 清理缓存失败

- 在 modal 内或 toast 中显示失败信息
- 已成功和失败的项目建议分开反馈

## 测试策略

第一版至少覆盖：

### Web 侧

- `常规设置` 顶级 tab 导航显示与切换
- 主题模式三选一交互
- 窗口行为两个开关交互
- 清理缓存弹层默认全选

### Sidecar 侧

- `generalSettings` 读写
- 日志目录路径打开调用
- 缓存清理接口按选项执行

### Desktop 侧

- 最小化到托盘行为
- 关闭到托盘行为
- 设置关闭后事件行为随之变化

## 未来扩展位

这个页面后续可以自然扩展：

- 语言
- 默认下载目录
- 通知
- 外链/文件打开确认
- 自动更新策略
- 界面密度

当前结构无需重做，只需继续往三个区块或新增第四个区块扩展。

## 最终结论

第一版采用：

- 独立顶级页 `常规设置`
- 作为设置默认入口
- 三组结构：界面 / 窗口行为 / 维护
- 持久化落在现有 `settings.json` 的 `generalSettings` 命名空间
- 主题与窗口行为真实生效
- 维护动作真实执行
- 清理缓存仅限安全缓存三项

这是当前最清晰、语义最稳、扩展成本最低的第一版方案。
