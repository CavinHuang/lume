# Subagent Message Routing Fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ensure one user input produces one visible parent message, user text never becomes a Subagent task implicitly, existing Subagent work continues across parent turns, and child output streams only inside its linked Subagent card.

**Architecture:** Separate the user-visible parent message from the model-facing continuation prompt, make Subagent creation an explicit state transition, and persist the coordinator-run to child-runtime-attempt links. Parent and child RuntimeEvents remain in their owning thread; the parent card reads the latest linked child runtime attempt instead of receiving copied child deltas.

**Tech Stack:** TypeScript, Bun tests, existing Sidecar JSON/run-state stores, Jotai; no new dependencies.

---

## Confirmed causes

1. `sendAgentMessage` persists the raw user text once, but a continuation run stores an expanded model-facing prompt. Both become `message.user.submitted` RuntimeEvents with the same `messageId`. Web deduplication compares text first, so both survive; reconciliation then replaces both with the same persisted text, rendering two `继续` messages.
2. `Agent` calls without `task_id` or `subagent_id` call `SubagentCoordinator.createWork`, which creates a real Session, Task, Run, and child thread. A generic `继续` prompt therefore becomes a new child task.
3. `SubagentRun.runId` is generated by the coordinator, while each `LumeRunObserver` attempt independently generates a child runtime `runId`. `projectSubagentRun` compares unrelated IDs and drops the real child stream.

## Required invariants

- One persisted parent user message maps to at most one visible user RuntimeEvent, keyed by `messageId`.
- Model-only continuation context is never displayed as another user message.
- A Subagent receives only a structured instruction explicitly dispatched by the main Agent.
- With unresolved work, creating an unrelated Task requires `new_task: true`; a continuation-only prompt without a target is rejected.
- Child events retain `threadId = childThreadId`; parent messages never project child deltas.
- A parent card locates child events by the latest persisted `runtimeRunIds` entry, not coordinator `runId`.

## Remaining compatibility risks

- Existing stored Runs do not have `runtimeRunIds`; historical cards should fall back to completed report summaries and must not guess from later child attempts.
- Old live sessions created before the fix may already contain a Task whose objective is `继续`; migration should preserve it for audit but mark it unresolved rather than silently attach it to another Task.
- Multiple unresolved Tasks must never be resolved by “pick the latest” heuristics. The main Agent receives the candidate IDs and must explicitly select one or ask the user.
