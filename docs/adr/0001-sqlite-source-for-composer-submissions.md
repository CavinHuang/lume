# 使用 SQLite 事件作为新输入提交的接收事实源

Lume 现有线程索引、会话 JSONL 和消息版本文件无法与提交收据、附件租约进行跨文件原子提交。即时逻辑提交只有在同一 SQLite 事务写入不可变用户消息事件、结构化消息部分、accepted 收据和待处理 outbox 后才算被接收；排队提交则在事务中写入完整、可恢复的队列快照、queued 收据和附件归属，直到队首被认领的事务才生成唯一消息事件与 outbox。现有文件格式继续作为可幂等重放的读取投影，历史消息不迁移。

## Considered Options

- 仅保留 receipt/lease journal，并接受进程崩溃边界上的重复或缺失：实现更小，但无法兑现响应丢失后安全重试和唯一消息语义。
- 将全部历史 Agent transcript 迁入 SQLite：一致性更彻底，但远超本次输入体验改造范围，也会扩大迁移和回滚风险。

## Consequences

新提交需要 outbox worker、投影幂等键、启动协调和数据管理生命周期；在这些环节完成前，现有半实现 outbox 不能被视为可靠接收证明。

已接收的不可变消息事件与提交收据随所属会话保留，并在删除会话时一并清除。JSON/JSONL 投影可以由事件重建，不承担长期去重依据。Outbox 在投影完成且运行时交接成功后清除重复的正文与附件载荷，只保留状态、关联 ID、时间和错误摘要；未完成或失败的 Outbox 保留完整载荷以支持重启恢复与人工重试。历史消息不迁移，也不另设按天过期策略。

已确认 queued 的快照也是接收事实源的一部分，不能在重启时丢弃。重启只把它恢复为暂停队列并等待用户确认，不自动执行；认领或终结后才清理重复载荷。
